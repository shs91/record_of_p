## 1. 비전과 문제 정의

사람은 "나중에 저기 가면 해야지"라고 생각한 일을 그 장소 앞을 지나면서도 잊는다(전향 기억, prospective memory 실패). P의기록은 **생각난 순간에 기록하고, 그 일을 처리할 수 있는 장소 근처를 지날 때 알림**으로 되살려주는 앱이다.

- 핵심 가치: "장소가 기억을 대신 트리거한다."
- 차별점: 기존 위치 리마인더(애플 미리알림 등)는 **특정 지점 1곳**에만 알림을 걸 수 있다. P의기록은 **"아무 편의점이나", "아무 다이소나"** 같은 카테고리/브랜드 단위 트리거가 핵심이다.
- 시장 근거: 글로벌 유사 앱(GeoReminder, GeoNote 등)은 Google Places 기반이라 한국 POI 품질이 낮다. 한국은 카카오 로컬 데이터로 정면 승부할 수 있는 공백 시장이다.
- 품질 원칙: **빠른 출시보다 좋은 사용자 경험.** 알림이 "귀신같이 맞게, 귀찮지 않게" 오는 것이 이 앱의 전부다. 오발화(엉뚱한 알림)와 미발화(지나쳤는데 침묵)를 줄이는 튜닝 루프를 설계 단계부터 내장한다.

### 1.1 성공 기준 (v1.0)
- 도보로 트리거 장소 앞을 지날 때 **80% 이상 발화** (필드 테스트 프로토콜 기준).
- 차량 통과·원거리 스침에 의한 오발화가 체감상 드물 것 (DWELL 필터로 차단).
- 하루 알림이 기본 정책(총 10건, 항목당 3건) 안에서 "유용했다"고 느껴질 것.
- 백그라운드에서 앱을 며칠 안 열어도 동작할 것 (헬스체크로 자가 복구).

## 2. 플랫폼 전략

**Android 네이티브(Kotlin) 선출시 → 검증 후 iOS 네이티브(Swift) 포팅.**

| 근거 | 설명 |
|---|---|
| 시장 표본 | 한국 Android 점유율 ~70%+. 검증 모수가 가장 크다. |
| 기술 여유 | 지오펜스 한도 Android 100개 vs iOS 20개. 넉넉한 한도에서 코어 품질(재배치·알림 정책)을 완성한 뒤, 검증된 파라미터로 iOS의 빡빡한 한도에 대응하는 순서가 품질 전략상 유리하다. |
| 역량 재사용 | 양쪽 네이티브 경험 보유. 크로스플랫폼(Flutter)은 핵심 차별화 기능이 정확히 "백그라운드 OS 동작"인 이 앱에서 추상화 계층이 리스크가 되므로 배제한다. |
| 포팅 대비 | 지오펜스 엔진을 **순수 Kotlin 로직**(플랫폼 API 무의존)으로 격리해 설계한다. iOS 포팅 시 같은 알고리즘을 Swift로 이식하고 예산 파라미터만 교체한다(§6.3). |

## 3. 범위

### 3.1 v1.0 포함
- 리마인더 항목 CRUD (제목, 메모, 트리거, 완료/보관)
- 트리거 3종: **카테고리**(빌트인 10종), **브랜드**(프리셋 2종 + 사용자 입력), **특정 장소**(카카오 키워드 검색으로 지점 선택)
- 항목당 트리거 다중 지정 (예: "휴지 사기" → 편의점 + 대형마트)
- 지오펜스 엔진: 동적 재배치(re-seeding), 센티널 이동 감지, 부팅/업데이트 재등록, 주기 헬스체크
- 알림 파이프라인: DWELL 필터, 쿨다운, 하루 상한, 방해금지 시간대, POI 그룹핑, 알림 액션(완료/오늘 그만)
- 주변 보기 화면 (현재 위치 기준 매칭 POI 리스트 + 카카오맵 앱 딥링크)
- 점진적 권한 온보딩 + 보호 상태 대시보드 + 진단(문제 해결) 화면
- 다크 모드, 한/영 리소스

### 3.2 v1.0 제외 (로드맵으로 이연)
- **v1.1**: 이동수단 감지(Activity Recognition — 권한 1개 추가 필요), 홈 위젯·빠른 설정 타일, 항목별 반경 커스텀 UI, 인앱 지도 뷰(카카오맵 SDK), 알림에서 "이 장소에선 그만" 액션, POI 응답 캐시
- **v2.0**: iOS 포팅, 기기 간 동기화(계정), 수익화(프리미엄)

### 3.3 빌트인 트리거 카탈로그

카카오 로컬 API는 카테고리 그룹 코드 검색과 키워드 검색을 제공한다(radius 최대 20km, 페이지당 최대 15건, 최대 45페이지, `sort=distance` 지원). 코드가 없는 업종은 키워드 검색으로 해석한다.

| id | 표시명 | 해석 방식 | 비고 |
|---|---|---|---|
| convenience | 편의점 | 코드 `CS2` | |
| mart | 대형마트 | 코드 `MT1` | |
| pharmacy | 약국 | 코드 `PM9` | |
| bank | 은행 | 코드 `BK9` | |
| post | 우체국 | 키워드 "우체국" | 코드 없음 |
| fuel | 주유소·충전소 | 코드 `OL7` | |
| laundry | 세탁소 | 키워드 "세탁소" | 코드 없음 |
| cafe | 카페 | 코드 `CE7` | |
| hospital | 병원 | 코드 `HP8` | |
| subway | 지하철역 | 코드 `SW8` | |
| daiso | 다이소 | 키워드 "다이소" | 브랜드 프리셋 |
| oliveyoung | 올리브영 | 키워드 "올리브영" | 브랜드 프리셋 |

- 사용자 커스텀 브랜드: 자유 키워드 입력(예: "GS25", "이마트24", "버거킹"). 키워드 검색 + `sort=distance`로 동작하므로 별도 구현 비용이 없다.
- 카탈로그는 코드에 내장(enum 성격의 정적 목록)하고 DB에 두지 않는다. 추가·변경은 앱 업데이트로 배포한다.

## 4. 사용자 경험 설계

### 4.1 핵심 플로우
1. **기록**: 홈 FAB → 제목 입력 → 트리거 선택(카테고리 칩 다중 선택 / 브랜드 입력 / 장소 검색) → 저장. **3탭 + 타이핑 이내**가 목표. 마찰이 낮아야 "생각난 순간 기록" 습관이 생긴다.
2. **알림**: 트리거 장소 근처에서 DWELL 조건 충족 → "📍 CU 역삼점 근처예요 (약 80m) · '건전지 사기' 외 1건". 액션 버튼 [완료] [오늘 그만]. 탭하면 해당 항목으로 딥링크.
3. **처리**: 알림에서 즉시 완료 처리하거나, 앱에서 스와이프로 완료. 완료 항목은 보관함으로.

### 4.2 온보딩 (점진적 권한)
가치를 먼저 보여주고 권한은 단계적으로 요청한다. 각 단계는 거부해도 앱이 동작하는 열화 모드(degraded mode)를 가진다.

| 단계 | 요청 | 거부 시 동작 |
|---|---|---|
| 1. 가치 소개 | 없음 (일러스트 2~3장) | — |
| 2. 알림 권한 | `POST_NOTIFICATIONS` (A13+) | 인앱 목록만 사용 가능 |
| 3. 위치(사용 중) | `ACCESS_FINE_LOCATION` | 주변 보기·지오펜스 불가, 목록 앱으로 동작 |
| 4. 홈 진입 후 업셀 카드 | 백그라운드 위치("항상 허용") | 앱을 열었을 때만 주변 확인 가능 |

- Android 11+에서 백그라운드 위치는 시스템 설정에서만 부여 가능 → 업셀 카드는 설정 화면 딥링크 + 단계별 안내 이미지로 구성한다.
- 배터리 최적화 예외는 **자동 요청하지 않는다**(플레이 정책 리스크). 설정 탭 "보호 상태"에서 삼성 절전 기능 등 제조사별 안내 화면으로 유도만 한다. 한국은 삼성 비중이 높아 이 안내 품질이 실사용 신뢰성을 좌우한다.

### 4.3 보호 상태 대시보드 (설정 탭)
알림 권한 / 위치 권한 / 항상 허용 / 배터리 최적화 예외 / 최근 엔진 동작 시각을 신호등으로 표시. 하나라도 꺼지면 홈 상단에 배너로 노출한다. "왜 알림이 안 오지?"에 대한 답을 앱이 스스로 제공해야 한다.

### 4.4 진단(문제 해결) 화면
엔진 실행 이력(EngineRunLog)과 최근 지오펜스 이벤트·필터 결과를 사람이 읽을 수 있게 표시. 필드 테스트 때 튜닝 도구이자, 출시 후 사용자 문의 대응 도구가 된다. 로그는 기기에만 저장되고 사용자가 수동으로 내보낼 수 있다(텍스트 공유).

## 5. 아키텍처

### 5.1 스택
| 영역 | 선택 | 근거 |
|---|---|---|
| 언어/UI | Kotlin + Jetpack Compose (Material 3) | UX 품질·생산성. 다크모드/동적 색상 무료 획득 |
| DI | Hilt | 표준. WorkManager·Receiver 주입 지원 |
| 저장 | Room + DataStore(설정) | 전량 로컬 |
| 네트워크 | Retrofit + OkHttp + kotlinx-serialization | 카카오 로컬 API 전용 |
| 위치 | play-services-location (GeofencingClient, FusedLocationProvider) | OS 관리 저전력 지오펜싱 |
| 백그라운드 | WorkManager (헬스체크·재시도), BroadcastReceiver (지오펜스/부팅/업데이트) | Doze 친화 |
| 빌드 | 단일 모듈 `app` + 패키지 경계, Version Catalog | 1인 개발에서 멀티모듈은 비용>이득. 경계는 패키지 규율로(§5.2) |
| SDK | minSdk 26 / compile·target 36 | 26 = 알림 채널 이후, 사실상 전 기기. target 36은 2026-08 Play 최신 요건 충족 |

### 5.2 패키지 구조와 의존 규칙
```
com.recordofp.app
├─ ui/            # Compose 화면, ViewModel, 내비게이션, 테마
├─ domain/
│  ├─ model/      # Reminder, TriggerSpec, CategoryDef 등 순수 모델
│  └─ engine/     # ★ 순수 로직: ReseedPlanner, NotificationGate (Android 무의존)
├─ data/
│  ├─ db/         # Room 엔티티·DAO·DB
│  ├─ poi/        # 카카오 로컬 API 클라이언트, DTO, PoiRepository
│  └─ repo/       # ReminderRepository, EngineStateRepository
└─ platform/      # Android 접착부: GeofenceClient 래퍼, Receiver, Worker, 알림 발행
```
의존 방향: `ui → data/repo → domain`, `platform → domain + data`. **`domain/engine`은 어떤 Android API도 import하지 않는다** (JVM 단위 테스트와 iOS 포팅의 기반). 시간은 `Clock` 주입, 난수·UUID도 주입.

### 5.3 데이터 모델 (Room)
| 테이블 | 필드 요지 |
|---|---|
| `Reminder` | id, title, memo?, status(ACTIVE/DONE/ARCHIVED), snoozeUntil?, createdAt, updatedAt, completedAt? |
| `TriggerSpec` | id, reminderId(FK), type(CATEGORY/BRAND/PLACE), categoryId?, brandKeyword?, placeName?, placeKakaoId?, lat?, lng? |
| `GeofenceReg` | geofenceId(PK, uuid), kind(SENTINEL/POI/PLACE), lat, lng, radius, poiName?, poiKakaoId?, matchKey(카테고리 id 또는 브랜드 키워드), reseedBatchId, registeredAt |
| `RegTrigger` | geofenceId ↔ triggerId (N:M — 한 POI가 '편의점' 카테고리와 'GS25' 브랜드를 동시에 만족할 수 있음) |
| `NotificationLog` | id, reminderId, poiKakaoId?, shownAt |
| `EngineRunLog` | id, at, cause(BOOT/SENTINEL_EXIT/PERIODIC/APP_OPEN/ITEM_CHANGE/RETRY), result, registeredCount, note |

POI 응답 캐시 테이블은 **v1에서 의도적으로 제외**한다. 실패 시 "직전 등록 유지 + 백오프 재시도"(§6.4)로 충분하며, 캐시는 무효화 복잡도를 들여올 가치가 v1.1에서 재평가되어야 한다.

## 6. 지오펜스 엔진 (핵심 설계)

### 6.1 제약과 전제
- Android 지오펜스 한도 **앱당 100개**. 지오펜스는 재부팅·앱 데이터 삭제 시 소멸하고, 앱 업데이트 후에도 재등록이 권장된다 → `BOOT_COMPLETED`·`MY_PACKAGE_REPLACED` 수신 시 재배치.
- 지오펜스 트리거는 OS가 셀/Wi-Fi 기반으로 저전력 처리한다. **앱이 스스로 위치를 폴링하는 코드는 금지**(배터리 원칙). 이동 감지조차 센티널 지오펜스로 해결한다(§6.2).
- 예산: `B_total=100` 중 센티널 1, 안전 여유 4를 제외한 **95개**를 POI/PLACE에 배분.

### 6.2 재배치(Reseed) — 언제
| 트리거 | 설명 |
|---|---|
| SENTINEL_EXIT | 마지막 재배치 좌표 중심 **반경 1.0km EXIT 지오펜스** 1개를 항상 유지. 이탈 = "크게 이동했다" 신호. 위치 폴링 없는 이동 감지 |
| ITEM_CHANGE | 항목/트리거 생성·수정·완료·삭제 |
| BOOT / PACKAGE_REPLACED | 재부팅·앱 업데이트 후 복구 |
| APP_OPEN | 앱 포그라운드 진입 시 기회적 실행 (조건: 마지막 재배치에서 500m+ 이동 또는 6시간+ 경과) |
| PERIODIC | WorkManager 6시간 주기 헬스체크. 등록 상태 검증 + 필요 시 재배치. 다른 신호가 다 죽었을 때의 최후 방어선 |
| RETRY | 직전 재배치 실패 시 백오프(15분→1h→6h) 재시도 |

디바운스: 재배치 최소 간격 10분(ITEM_CHANGE는 예외 — 즉시 반영하되 30초 코얼레싱).

### 6.3 재배치 — 무엇을 (ReseedPlanner, 순수 로직)
입력: 활성 트리거 목록, 현재 좌표, 예산 B=95. 출력: 등록할 지오펜스 집합(순수 데이터).

1. **PLACE 트리거**: 각 1개씩 무조건 등록(거리 무관 — 등록 비용은 동일하고, 사용자가 명시한 지점은 언제 가도 울려야 한다). 예산 초과 시 가까운 순.
2. **CATEGORY/BRAND 트리거**: 트리거별로 현재 위치 반경 **2.0km** POI 조회(`sort=distance`, 최대 2페이지=30건). 조회 반경(2.0km) > 센티널 반경(1.0km)이므로 센티널 이탈 전까지 커버 공백이 없다.
3. **중복 병합**: 서로 50m 이내의 동일 matchKey POI는 하나로 병합. 서로 다른 트리거가 같은 POI를 매칭하면 지오펜스 1개에 RegTrigger N:M로 연결.
4. **예산 배분**: 남은 예산을 트리거 수 T로 균등 분할(트리거당 상한 20). 후보가 모자란 트리거의 잔여분은 2차 패스에서 다른 트리거에 재배분.
5. **반경/전이 정책**:
   - CATEGORY/BRAND: 반경 **120m**, `DWELL(loiteringDelay 60초)`. 도보 통과(속도 ~5km/h, 체류 ~170초)는 잡고 차량 통과(체류 ~20초)는 거른다. 이 값이 오발화/미발화 튜닝의 1차 파라미터다.
   - PLACE: 반경 **150m**, `ENTER`(사용자가 그 지점을 명시했으므로 진입 즉시).
   - SENTINEL: 반경 1.0km, `EXIT`.
6. **적용**: 현재 등록분과 diff → removeGeofences/addGeofences 최소 호출. 전체 교체가 아니라 차분 적용으로 이벤트 유실 창을 줄인다.

**iOS 포팅 노트**: 동일 알고리즘에 파라미터만 교체한다 — B=18(한도 20 - 센티널 1 - 여유 1), 조회 반경 1.5km, 트리거당 상한 6. 엔진이 순수 로직인 이유가 이것이다.

### 6.4 실패 처리
- 카카오 API 실패/오프라인: **기존 등록을 지우지 않는다**(구 데이터가 무등록보다 낫다). EngineRunLog에 기록하고 RETRY 백오프 예약.
- 위치 미취득(실내 등): FusedLocation `getCurrentLocation(BALANCED)` 1회 시도 → 실패 시 lastLocation → 그것도 없으면 재배치 보류 + RETRY.
- 권한 회수 감지: 헬스체크에서 권한 상태 확인 → 회수 시 등록 전부 해제하고 보호 상태 대시보드에 반영(고아 지오펜스 방지).
- 카카오 일 쿼터(로컬 API 무료 일 10만 건) 방어: 재배치당 호출 수 = 트리거 수 × ≤2. 사용자당 하루 수십 회 수준이라 v1 사용자 규모에선 여유. 429/403 응답은 API 실패와 동일 경로로 처리.

### 6.5 이벤트 파이프라인 (NotificationGate, 순수 로직)
`GeofenceBroadcastReceiver`(goAsync) → 파이프라인:
1. 이벤트의 geofenceId가 현재 등록 테이블에 유효한지 검증 (stale 이벤트 폐기)
2. RegTrigger → TriggerSpec → 활성 Reminder 로드
3. **필터 체인** (각 단계 통과/차단을 EngineRunLog에 기록 — 진단 화면에서 "왜 안 울렸는지" 보이게):
   상태(ACTIVE인가) → 스누즈/오늘그만 → 방해금지 시간대 → 항목 쿨다운(4h) → 항목·지점 쿨다운(24h) → 항목당 하루 상한(3) → 전체 하루 상한(10)
4. 통과 항목을 POI 단위로 그룹핑해 **알림 1건** 발행(항목 나열). 알림 채널 분리: "근처 알림"(높음), "서비스 상태"(낮음)
5. NotificationLog 기록

## 7. 카카오 로컬 API 연동
- REST 키는 `local.properties`의 `KAKAO_REST_KEY`로 주입(BuildConfig). 저장소에 커밋하지 않는다. 발급: developers.kakao.com에 앱 등록 → REST API 키.
- 사용 API: 카테고리 검색(`/v2/local/search/category.json`), 키워드 검색(`/v2/local/search/keyword.json`). 공통 파라미터 x, y, radius(≤20,000m), size(≤15), page, sort=distance.
- 응답 중 사용 필드: `place_name, category_group_code, road_address_name, x, y, distance, id, place_url`.
- 좌표는 조회 시에만 전송하고 서버에 저장하지 않는다(우리 서버 자체가 없음). 약관상 검색 결과의 영구 저장·재배포는 피하고, 등록 지오펜스에 필요한 최소 필드(지점명·좌표·id)만 기기에 보관한다.

## 8. 접근성·국제화
- 한국어 기본, 영어 리소스 동시 제공(`values`, `values-en`). 앱 이름: P의기록 / Record of P.
- TalkBack 콘텐츠 설명, 48dp 터치 타깃, 폰트 스케일 대응(모든 텍스트 sp).
- 지역 확장은 POI 공급자 추상화(PoiRepository 인터페이스)로 대비만 해두고 v1은 카카오 단일 구현.

## 9. 프라이버시·보안
- 위치·항목 데이터는 기기 밖으로 나가지 않는다. 유일한 외부 통신은 카카오 POI 조회(좌표 전송, 무저장).
- 분석·광고 SDK 없음. Play 데이터 안전 섹션 "수집하는 데이터 없음" 포지션 — 백그라운드 위치 앱의 심사·신뢰 관점에서 가장 강한 카드다.
- 백그라운드 위치 권한 선언(Play Console 정책 폼) + 기능 시연 영상 필요. "위치 기반 리마인더"는 인정되는 사용 사례다.
- 프라이버시 정책 문서(호스팅 URL 필요)는 출시 체크리스트에 포함(§10).

## 11. 출시 계획 (Google Play)
1. **비공개 테스트 요건**: 신규 개인 개발자 계정은 **테스터 12명, 14일 연속 옵트인** 후 프로덕션 신청 가능. 테스터 모집 계획을 개발 후반부에 준비(지인 + 테스터 교환 커뮤니티).
2. 백그라운드 위치 권한 선언 폼 + 데모 영상(온보딩→업셀→알림 수신 흐름 녹화).
3. 데이터 안전 폼("수집 없음"), 프라이버시 정책 URL 호스팅.
4. target SDK 최신 요건 확인(36으로 개발 중 — 출시 시점에 재확인).
5. 스토어 리스팅: 스크린샷 6장(핵심 플로우), 그래픽 이미지, 소개문.
6. 상표 확인: "P의기록/Record of P"는 게임 'P의 거짓(Lies of P)'과 상품 분류가 다르나, 출시 전 키프리스 간단 검색을 권장.
7. 카카오 developers 앱 등록·키 발급, 플랫폼(Android 패키지명) 등록.

## 13. 열린 질문 (구현 중 확정, 차단 아님)
- 카카오 로컬 무료 쿼터(일 10만)의 상업 서비스 조건 재확인 — 사용자 급증 시 비즈 앱 전환 필요 여부 (출시 전 확인 항목).
- `loiteringDelay`/반경 최종값 — 필드 테스트로 결정 (§10.2), 설계상 기본값은 60s/120m.
- 브랜드 키워드 검색의 오탐(예: "GS25" 검색에 GS타워 매칭 등) 정도 — 필드 데이터로 확인 후 `category_group_code` 교차 필터 추가 여부 결정.
